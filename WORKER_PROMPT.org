#+title: Seal v0 Worker Handoff

* Purpose

Implement one assigned Seal v0 ticket in one isolated worktree. Produce a small,
reviewable PR and durable evidence, then stop.

Seal v0 transports one opaque mailbox tree through local or SSH rsync semantics.
It does not interpret, approve, attest, classify, or execute mailbox content.
Planning PR #1 is the reviewed contract surface, not an implementation car:

https://github.com/engimatic-systems/seal/pull/1

* Dispatch record

The coordinator must fill this block before handing work to a worker:

#+begin_example
epic: sys-cv8p
ticket: TICKET_ID
car: CAR_NUMBER
worktree: /home/rosin/sys/working/sys-cv8p/CAR-seal-NAME
branch: review/CAR-NAME
target: integration/v0
expected_base: COMMIT
pr: unset
#+end_example

Verify the worktree branch, target, and base commit before editing. Stop and
report a mismatch; do not repair train topology from a worker task.

* Authority

Read these surfaces before implementation, in this order:

1. =SPEC.org=: normative v0 behavior and non-claims.
2. Assigned tko ticket: current car scope, exclusions, acceptance, and evidence.
3. =PLAN.org=: sequence and review question.
4. =SEAL.org=: canonical literate implementation source once car 001 creates it.

Chat, generated Rust files, and implementation convenience do not override
those sources. When the spec, ticket, and plan conflict or leave a consequential
contract ambiguous, record the conflict and stop instead of choosing policy in
code.

* Train topology

The operator first merges planning PR #1. The coordinator then creates
=integration/v0= from that merged default branch. Do not create the integration
branch from an unmerged planning head.

Cars are serial. Each review branch starts from the then-current
=integration/v0= only after the preceding car is operator-approved and landed.
Each PR targets =integration/v0=. Do not prebuild tail branches.

|-
| 001 | sys-ujis | review/001-executable-seed | 001-seal-executable-seed | Literate executable seed |

Do not merge PRs. Do not advance or retarget the train unless the operator asks.

* Role boundary

The operator approves each car and any movement of the train. The coordinator
creates integration state and worktrees, dispatches one ready ticket, verifies
integration-critical evidence, updates ticket status, and lands only approved
work.

The worker edits only the assigned worktree, implements one ticket, runs
accumulated checks, commits, pushes, opens a PR against the dispatched target,
and records evidence. The worker may add a readable evidence note to the ticket
and run =tko lint TICKET_ID=. The worker does not close the ticket.

* Literate source discipline

- Edit =SEAL.org= first for handwritten implementation, test, and build
  definitions. Do not hand-edit a tangled output into a divergent source.
- Put reviewer-facing pseudocode immediately before consequential source blocks.
- Split blocks only at stable file or top-level Rust boundaries.
- Make tangled outputs identify =SEAL.org= as their source.
- Keep =Cargo.lock= as generated dependency output outside literate ownership.
- Tangle twice. The second tangle must leave no unexplained diff.
- Add an abstraction or dependency only when the current car needs it. Record
  the reason when it enlarges the review surface.

* Hard boundaries

Every car excludes automated execution, proposal/result schemas, approval,
attestation, reusable shapes, mailbox interpretation, deletion propagation,
configurable ordinary transfer flags, background behavior, multiple mailboxes,
credential management, and any transport other than the specified local/SSH
rsync path.

Car-specific boundaries:

- 001: no config, mailbox, SSH, rsync, or later-verb stubs.
- 002: no filesystem creation, peer contact, or external process execution.
- 003: no peer contact, peer provisioning, transfer, or global state.
- 004: pull only; no push, retry, rollback, dereference, delete, or content use.
- 005: reverse direction only; no publication or result semantics.
- 006: no transfer dry-run, write probe, setup, repair, or mutation.
- 007: validation and contract-required defect repair only. Use disposable state,
  keep =agent-dayjob-01= powered off, and do not claim VM lifecycle authority.

New config fields, passthrough flags, automatic behavior, mutation in =doctor=,
or another transport are stop conditions. Update the spec for operator review
before implementing any contract change.

* Required evidence

Before handing the car back, provide:

- branch, base commit, final commit, PR URL, and PR base;
- concise changed-file and behavior summary;
- first-tangle result and clean second-tangle result;
- formatter, accumulated test, and build commands with exit status;
- car-specific plan snapshots, CLI transcripts, fixtures, or live observations
  required by the ticket;
- explicit residual risks, unsupported claims, and unresolved questions; and
- clean worktree status apart from intentional committed artifacts.

Mocked process tests do not substitute for car 007 live evidence. Live evidence
does not expand the behavioral claim beyond =SPEC.org=.

Record durable results from =/home/rosin/sys= with a short titled note:

#+begin_src sh
PATH=/home/rosin/.local/bin:$PATH \
  tko add-note --title "Implementation evidence" \
  --body "BRANCH, COMMIT, PR, COMMANDS, RESULTS, RISKS" TICKET_ID
PATH=/home/rosin/.local/bin:$PATH tko lint TICKET_ID
#+end_src

Use readable Org in the actual note body; the example names required content,
not a literal one-line format.

#+title: Seal context: v0.1 wayfinding and grilling record
#+date: 2026-07-16
#+options: toc:3 num:nil

* What this document is

This is a record of an exploratory grilling session around the next movement
after Seal v0.  It preserves questions, arguments, corrections, and current
leanings.  It is not a specification, decision ledger, implementation plan, or
claim that the vocabulary below has settled.

The discussion is trying to clear fog around a usable one-shot command flow.
Premature precision would erase useful ambiguity.  Where the conversation has
not reached an answer, this document should leave the question open.

The evidence under discussion is:

- [[file:README.org][Seal v0]], particularly its opaque mailbox transport and its
  earlier design doctrine;
- [[file:../airlock/][Airlock]], especially
  [[file:../airlock/train-audit.org][the adversarial train audit]];
- [[file:../mailbox.zip][the captured day-job mailbox]]; and
- [[file:../MAILBOX.org][the account of how that mailbox is used]].

"v0.1" is a useful name for the area being explored.  It may be more honest
than calling the next movement a hardened v1 before its product shape is known.

* Where the discussion began

Seal v0 is a minimal host-initiated transport.  Its operative specification
deliberately does not represent proposals, world facts, attestations,
executions, or results.  Its earlier design documents nevertheless describe a
trace in which an exact proposal =P= is reviewed under material world facts
=W=, explicitly authorized as =A=, executed as =E=, and reported as =R=.

Airlock attempted to move much farther at once: reusable command shapes,
contexts, matching, an attestation store, several proposal types, a consumer,
and a review interface.  Its audit found that the operator-side attestation
path arrived late and did not bind the displayed evidence to the eventual
authority mutation.  More broadly, Airlock accumulated several authority and
execution paths before one action-instance path was sound.

The first read of these materials suggested returning to a one-shot,
exact-proposal path.  The mailbox then complicated the picture in productive
ways.

* Is the current mailbox already =P, W, A, E, R=?

** Question

Does the mailbox's informality mean that it lacks the Seal trace, or is it
already a manual realization of that trace?

** Rosin's account

The mutable mailbox directory functions as =P=.  The operator opens its regular
files, reads the runbook and scripts, and refuses by declining to run them.

=W= is a known host runtime context associated with the mailbox by filesystem
locality.  In the day-job instance, entering the mailbox also enters a scoped
=mise= environment with pinned tools and environment reconciliation.

Execution is the operator running selected material from the mailbox.  Output
files land wherever those scripts put them.  Those files are not necessarily
durable: another invocation may overwrite them.  Standard output, standard
error, and attempt status are recognizable result material even when the
current workflow does not retain them systematically.

** Present understanding

The mailbox is a functioning manual reference system.  Its identities live in
operator attention and timing rather than in Seal.  That difference matters
for hardening, but it does not make the current workflow semantically empty.

The runbook-shaped surface may also be contingent rather than essential.  It
arose partly because the agent has no way to request one particular command.
Numbered scripts, intermediate checks, and abundant debug output make a
multi-step request tractable through a weak channel.  Once individual command
proposals exist, some of this shape may dissolve.

* Narrow first, or minimal first?

** Question

Should Seal begin with a narrow execution contract and cautiously widen it, or
with a minimal permissive contract and add constraints when actual friction
reveals their value?

** Narrow-first approach

A narrow-first Seal might execute only inside =bwrap=, expose a fixed tool set,
provide a fixed environment, and admit only a constrained command language.
This gives automation a mechanically bounded world.  The cost is having to
guess the useful boundary before the workflow has taught us what it needs.

** Minimal-first approach

A minimal-first Seal admits arbitrary one-shot commands under an operator-known
runtime profile.  Safety remains substantially an ad-hoc operator judgment:
the operator reads the exact proposal and chooses whether to run it.  Productive
constraints enter later when they remove observed friction, make a recurring
judgment mechanical, or enable automation without concealing consequence.

** Current leaning

Rosin leans minimal-first during exploration.  This is continuous with Seal's
existing doctrine: begin with the smallest complete manual truth, then admit
abstractions only when they preserve that truth and answer concrete pressure.

This does not answer what irreducible input, lifecycle, or storage hygiene a
first implementation needs.  It does reject choosing a full containment and
world model merely because those would make a later automation story tidier.

* May an execution mutate =W=?

** Question

If later proposals depend on a writable host workspace, is a proposal allowed
to change the world in which subsequent proposals run?

** Example

An early interaction may look like:

#+begin_example
P1: clone the Terraform repository
P2: run a plan inside the cloned repository
P3: apply the saved plan
#+end_example

=P1= exists precisely to change the conditions available to =P2=.  A system
that forbids this has probably excluded the first workflow an agent will try to
reconstruct.

** Present understanding

Nothing in a propose--attest--execute flow inherently requires =W= to remain
unchanged.  Executions have consequences; some consequences establish useful
state for later executions.

There remains a meaningful difference between two kinds of writability:

- the agent directly writes a host execution workspace; and
- an exact agent proposal, after operator attestation, causes a host execution
  to write that workspace.

The second is compatible with the intended mediation even when it produces a
persistent, stateful workspace.  It recreates some shared-workspace semantics
without necessarily recreating direct shared write authority.

This observation corrected an earlier suggestion to defer shared-directory
intake wholesale.  Mutable local intake may be central.  The live question is
how intake, execution material, and persistent host state relate—not whether
all directory-shaped interaction should be excluded.

* Must Seal represent =W= explicitly?

** Question

Does Seal need a first-class model of repositories, workspace revisions,
credentials, environment state, and other world objects?  Or can =W= remain
largely implicit in filesystem locality and a runtime profile known to the
operator?

** Argument for explicit objects

If repositories become first-class world objects, facts such as origin, HEAD,
and dirty state could make later review more intelligible.  Similar adapters
might expose other domains.  This could eventually support mechanical
invalidation and more automation.

** Argument for implicit =W=

There is no evident stopping point to a general world model.  Repository state
is only one influence.  Effective credentials, current cloud state, tool
behavior, network responses, time, and external code all affect consequence.

Even a concrete credential example resists byte identity: the Azure access
token used by two otherwise equivalent invocations will change.  "These exact
token bytes are present" is less useful than "the environment has reconciled a
working =az login=".  Exhaustive workspace identity therefore threatens to
become a black hole of effort without producing an honest snapshot of the
world.

** Current leaning

Keep =W= implicit initially: a known runtime profile reached through the
mailbox's filesystem location and its scoped environment.  Discover which
world facts deserve first-class treatment through use.

Repository HEAD, dirty state, workspace generations, and similar ideas remain
possible later tools.  They are not assumed prerequisites for v0.1.

* Could reconciliation be the first named piece of =W=?

** Question

Is there a useful middle ground between an entirely ambient world and an
exhaustive world representation?

** Proposal under discussion

A /world-reconciliation recipe/ could be an exact sequence of operations that
tries to establish the assumptions under which later commands run.  "Recipe"
here does not imply a shell language; it means executable operations.

The recipe might perform such work as tool materialization, credential login,
or environment repair.  It could permit arbitrary commands and pass through
the same proposal, operator-attestation, and execution path as any other
proposal.  Its exact bytes or representation could be named and hashed.

This would not capture the whole world.  It would give agent and operator a
minimal shared statement: this named reconciliation was run, with this result,
before subsequent work.

Airlock contained both a =mise= recipe backend and environment reconciliation.
Those ideas may still be useful even though Airlock's surrounding authority
system failed.  Its audit supplies one caution: if external reconciliation code
affects execution but its identity is omitted from the context evidence, the
named context says less than it appears to say.

** Questions left open

- Is reconciliation proposed by the agent, configured by the operator, or
  sometimes either?
- Does every changed recipe require ordinary one-shot attestation?
- Does Seal run reconciliation only when explicitly requested?
- Could it run implicitly before review or before execution?
- If it runs implicitly, what did the operator attest: the proposal, the
  recipe, their composition, or a remembered convention?
- Is a successful reconciliation an observation, a mutation of =W=, part of
  =R=, or all three?

No answer has been chosen.  The recipe is presently a way to think about a
small, named foothold in an otherwise implicit world.

* Where is the boundary between =W= and =R=?

** Question

When a command produces files that later commands consume, are those files
results, workspace, or future proposal material?

** Current account

A lifecycled command directory offers a useful local distinction:

- standard output, standard error, and attempt status are =R=;
- files deliberately placed in the command directory can travel back with
  that directory as result material;
- mutations outside the command directory are mutations of =W=; and
- if a later proposal copies or marshals earlier result bytes, such as a saved
  =plan.bin=, into its own proposed material, those copied bytes become part of
  the later =P=.

This is a promising intuition, not yet a complete rule.  A saved plan can be
both evidence returned to the agent and persistent input in the host workspace.
The current mailbox already permits output clobbering.  Whether v0.1 makes
=R= durable, transports whole command directories, or distinguishes declared
artifacts remains open.

* What should happen with filesystem-hierarchical =mise= discovery?

** Question

Should Seal freeze or constrain environment discovery so that later workspace
contents cannot alter the effective runtime profile?

** Current leaning

Probably not yet.  Filesystem-hierarchical =mise= discovery is part of the
present workflow and may remain implicit in v0.1.

A cloned repository could introduce nested configuration and thereby alter the
environment of a later command.  That is a real consequence.  During this
exploratory phase, it may remain one of the facts the operator is responsible
for understanding rather than becoming an immediate Seal restriction.

Experience may later show that effective environment resolution deserves a
named review surface or a constraint.  The discussion has not established
that point yet.

* May attested code modify Seal itself?

** Question

If Seal runs arbitrary operator-attested commands, must it prevent those
commands from changing =seal.toml= or a future Seal state directory?

** Permissive argument

An arbitrary-command runner is expected to admit some commands that alter its
surrounding host.  Modifying Seal configuration could be an intentional
operation.  On a minimal-first account, the operator is responsible for not
attesting a proposal that compromises Seal unintentionally.

** Protective argument

If an executed command can rewrite the state through which later proposals are
attested, an earlier execution can influence future authority.  Protecting
Seal's own configuration and authorization record might therefore be an
internal integrity boundary rather than a general claim that arbitrary code is
safe.

Meaningful protection would likely require an OS-enforced boundary: another
identity, mount restriction, sandbox, or equivalent.  A path check inside Seal
cannot constrain arbitrary code after launch.

** Current leaning

Do not introduce that prohibition yet.  Preserve it as a visible tension and
make no claim that a same-authority arbitrary command cannot modify Seal.
Observed use may later justify protecting a narrow Seal-owned directory even
while leaving the rest of =W= permissive.

* What remains from the Airlock lesson?

Airlock should not be reduced to "constraints are bad".  Its failure provides
several useful negative results:

- reusable shape authority was designed before the one-shot operator path was
  sound;
- adding an operator-side attestation command late did not repair evidence
  substitution or multiple execution paths;
- a displayed review and a confirmation must concern the same object; and
- environment and reconciliation machinery can create false confidence when
  their real inputs are not the inputs being named.

The present exploration does not yet turn those lessons into a new store,
state machine, or command surface.  The immediate positive hypothesis is
smaller: let an agent propose a specific command, let the operator inspect and
attest that proposal, run it once in the locally understood context, and return
its result.

* Could the first broker be throwaway shell machinery?

** Question

Does exploratory use require committing immediately to a durable implementation
of the whole command broker?

** Hypothesis

The first one-shot broker could plausibly be a mutable, operator-owned shell
script built on Seal's existing pull and push semantics.  That script could be
changed rapidly while trying different proposal shapes, review interactions,
reconciliation behavior, command-directory lifecycles, and result layouts.

"Mutable" here means easy for the operator to revise.  The script must remain
outside the agent-writable mailbox; otherwise experimental porcelain would
itself become proposal-controlled execution machinery.

This suggests an uneven implementation on purpose.  Queue scanning, prompts,
pagers, naming, and publication may be throwaway.  The final transition from an
attested object to a process launch cannot be equally loose.

** The firm waist

The exact boundary is still under discussion, but the =exec= operation would
need to preserve a few truths while the surrounding experiment changes:

- launch the host-held proposal that was actually inspected and attested, not
  a path the peer can still mutate;
- consume the exact invocation chosen by the operator rather than reconstruct
  it from changed ambient input;
- give one attestation at most one launch attempt;
- distinguish "not launched" from "launch began but outcome is unknown"; and
- attribute captured status and output to that proposal, attestation, and
  attempt.

Whether that firm waist is initially a careful shell routine, a small separate
helper, or some other throwaway-but-auditable mechanism is open.  The useful
split is not "prototype versus correctness."  It is "semantics currently being
discovered" versus "the one transition whose looseness would make the
experiment report false results."

* A concrete manual broker sketch

Everything in this section is disposable experimental machinery.  Concreteness
lets the discussion expose races and missing semantics; it does not imply that
the mailbox layout, locking convention, rsync choreography, or shell broker is
converging on the correct shape.  A useful experiment may be rejected after it
teaches one fact.

** Proposed mailbox shape

The first shell broker could use a deliberately small mutable layout:

#+begin_example
mailbox/
  ready/<command>/cmd.toml
  claimed/<command>/cmd.toml
  claimed/<command>/result.toml
  output/<command>.out
  output/<command>.err
  world/
#+end_example

=cmd.toml= contains an explicit argv list.  =world/= is shared mutable working
state for such things as a cloned Terraform repository and generated plans.

This was the first concrete sketch.  The implemented spike below deliberately
changes its execution unit from =cmd.toml= argv to one =command.sh=.

At this stage there was no watcher or poll loop.  The operator manually invoked
=seal-exec.sh= when ready to consider one command.

** Proposed interaction

The rough flow is:

#+begin_example
seal pull
inspect ready commands
claim one command
display its exact argv
require the operator to type "yes"
run it
capture stdout and stderr under output/
write result.toml
seal push
#+end_example

The surrounding script may remain quick and dirty.  It need not decide whether
an argv is safe or build a command-policy language.  The operator reads the
proposed invocation and refuses dangerous or surprising commands.  This is an
intentional use of operator judgment during discovery, not an assertion that
the script has validated arbitrary command safety.

** Initial implemented spike revision: one =command.sh=

Further grilling moved the experiment closer to the usability of the original
mailbox.  One command is now a directory containing a single =command.sh=:

#+begin_example
mailbox/
  ready/<command>/command.sh
  claimed/<command>/command.sh
  claimed/<command>/result.toml
  output/<command>.out
  output/<command>.err
  world/
#+end_example

The attestation granularity is one reviewed shell script.  That script may
perform several sequenced operations or execute sibling scripts.  This is
tighter than the old numbered-script runbook window but deliberately broader
than a single argv vector.

The operator may type =edit= before attestation; =seal-exec.sh= opens the
claimed =command.sh= in hard-coded =vi=, then redisplays the resulting bytes.
Scripts over 40 lines receive a warning rather than a refusal.

For simplicity and usability, the proposed command receives a writable bind of
the whole mailbox inside =bwrap=, not only =world/=.  This permits ad-hoc result
files in the claimed command directory.  It also lets the command alter other
mailbox material.  The experiment accepts that broader risk under operator
judgment rather than claiming mailbox-internal isolation.

The shell remains outside the mailbox.  After operator confirmation it copies
the approved =command.sh= to a host-only attempt directory and mounts that copy
read-only over the claimed script path during execution.  Host filesystem paths
outside the mailbox are mounted read-only; network and external authority are
not constrained.

The initial spike also included an explicit =purge= operation.  It removed local
=ready/= and built a queue-scoped =rsync --delete= invocation that emptied only
peer =ready/=, leaving the rest of the mailbox outside that destructive sync.
This is operator-requested destructive cleanup, not ordinary claim propagation.

The larger scope and weaker mailbox isolation are intentional.  They move the
experience closer to the intended workflow so the experiment can reveal useful
friction.  They are not a claim that this is the eventual Seal boundary.

** Friction from retry and merge-only history

*** Observation

Early use immediately exposed two related liabilities.  There was no useful
operator-side retry mechanic, and failed or obsolete material accumulated
because ordinary Seal transfers merge trees rather than propagate deletion.

An execution retry and a result-publication retry are not the same operation.
Re-executing old bytes may repeat an external effect.  Republishing evidence
should not execute anything.  A transport failure after launch can leave an
unknown outcome that permits neither blind replay nor ordinary progress.

*** Fail-forward answer

Rosin prefers fail-forward over a privileged execution retry.  If the agent
proposes one small command at a time, a known failure becomes evidence for the
next proposal:

#+begin_example
command fails
  -> preserve result and changed world
  -> agent observes them
  -> agent proposes one corrective command under a new ID
  -> operator attests the new consequence
#+end_example

Even an intentional repetition is a fresh proposal and receives fresh review.
This favors small commands over heavy scripts.  The useful unit is not exactly
one argv or a line limit; it is one consequence that can be understood and
corrected independently.

Old attempts may remain as evidence.  Their accumulation is then history, not
queue state.  Destructive cleanup can be explicit maintenance rather than a
precondition for protocol correctness.

** Watched operator-agent dialogue

*** Hypothesis

Two polling loops can form a lockstep dialogue through the mailbox.  The agent
publishes one command and polls for its result.  The operator-side broker polls
for a fresh command, stops for =yes= or =edit= attestation, executes it, and
publishes the terminal result.  The agent then proposes the next command.

The loop automates availability and result transport, not authorization.  A
known command failure is returned and watching continues.  A pull or push
failure stops the broker; a failed post-execution push must never cause
automatic re-execution.

*** Multiple proposals signal drift

The expected cardinality is one unclaimed proposal.  If several appear, strict
newest-first behavior applies.  Merely choosing newest would be insufficient:
the next watch iteration could otherwise execute the remaining commands in
reverse order.

The current spike therefore marks every older simultaneously visible proposal
=superseded=, names the winning command, and executes none of them.  The newest
proposal alone reaches operator review.  Surviving peer-side =ready/= copies
remain ineligible because same-ID =claimed/= markers win.

*** Full mailbox reset

Queue-scoped purge was too narrow for rapid experimentation.  The current
=purge= operation is an explicit reset: after literal confirmation it stages a
fresh mailbox containing =contract.org= and empty =ready/=, =claimed/=,
=output/=, and =world/= directories, deleting-syncs that shape to the peer,
then replaces the local mailbox.  Host-only attempt evidence remains outside
the reset.

This operation deliberately destroys history and world state.  It still has no
distributed lock, so operator and agent must coordinate quiescence around it.

** Current argv experiment

*** Pressure away from implicit shell

The fail-forward dialogue points back toward tiny commands and away from heavy
scripts.  Once sequencing moves into successive observed turns, arbitrary Bash
is no longer the natural default proposal language.  Its splitting, expansion,
redirection, and control flow enlarge the attestation surface even when the
intended consequence is one ordinary process invocation.

Rosin proposed returning to TOML argv.  The current spike now uses one
=command.toml= containing exactly one nonempty string array:

#+begin_src toml
argv = ["git", "-C", "terraform", "status", "--short", "--branch"]
#+end_src

There are no cwd, environment, stdin, pipeline, or sequencing fields.  A shell
remains an ordinary explicit executable, for example =argv = ["bash", "-lc",
"..."]=.  This preserves the permissive arbitrary-command boundary while
making shell interpretation visible.

*** Ambient environment remains part of =W=

Rosin requires commands to receive ambient environment variables.  The broker
therefore inherits =PATH=, credentials, active =mise= state, and other variables
from the operator process.  It serializes none of their values into the
proposal or result and continues to override =TMPDIR= beneath =world/=.

A long-running watch process captures its environment at startup.  Changes in
another shell, or new filesystem-hierarchical environment configuration, do
not mutate that process environment.  The present refresh mechanism is to
restart watch from a reconciled operator context.  Per-command reconciliation
remains a possible later experiment, not an implicit behavior.

*** Firm parse and execution waist

The broker snapshots =command.toml= before attestation, parses that snapshot
without =eval= or shell re-parsing, displays both exact source bytes and each
parsed argument, and holds the parsed vector through =yes=.  =edit= creates a
new snapshot and repeats parsing and display.  Invalid or additional fields
cannot execute.

The approved snapshot moves into host-only attempt evidence and is mounted
read-only over the claimed proposal.  The held argv vector executes directly
through =bwrap=.  This narrows representation ambiguity; it does not make the
named executable or inherited authority safe.

** A filesystem-write guard

One proposed safety measure is to execute through =bwrap= with host paths
read-only and writes allowed only inside =mailbox/=.  This would constrain a
command's filesystem mutations without yet trying to constrain its command
language, tools, network activity, cloud authority, or every source of ambient
state.

That is a useful but limited claim.  A command with network and credentials may
still mutate Azure or disclose readable data.  The boundary says where the
process can write on the local filesystem, not that the command is harmless.

** Tensions revealed by the sketch

*** A transported rename is not yet a rename

Seal v0 intentionally does not propagate deletions.  If the operator locally
moves =ready/X= to =claimed/X= and then pushes, the peer receives the claimed
copy but retains =ready/X=.  A later pull can recreate the local ready entry.

Adding whole-tree =rsync --delete= does not safely repair this.  Rsync deletes
receiver-side entries that are absent from the sender within synchronized
directories.  Consider this interleaving:

#+begin_example
operator pulls ready/X
agent publishes ready/Y
operator moves local ready/X to claimed/X
operator pushes its now-stale mailbox with --delete
#+end_example

During the push, the operator mailbox is the sending side.  The agent's new
=ready/Y= exists only on the receiving side, so =--delete= may remove it.  The
various delete timing modes change when deletion occurs, not the underlying
ownership mistake.  A bidirectional, concurrently written mailbox cannot use
whole-tree mirror deletion to express a one-party queue transition.

Possible exploratory responses included treating =claimed/X= as a marker that
makes any surviving =ready/X= ineligible, copying rather than pretending the
transport performed a move, asking the agent to clean acknowledged ready
entries, or later adding a queue-specific mutation.  The current spike selects
the additive claimed-marker interpretation; deletion remains maintenance.

*** Late reconciliation of =ready/=

A next-least-complex iteration could finish the command first, pull only
=ready/= again, prune local =ready/X= wherever =claimed/X= now exists, then
push only =ready/= with =rsync --delete=.  Commands published before that
second pull would be preserved in the local source and returned to the peer.

This materially narrows the destructive race.  It does not remove it.  A
command published or modified after the second pull but before the delete-push
can still be deleted or overwritten by the stale local tree.

The specialized final push exceeds Seal v0's fixed whole-mailbox transfer
profile.  An exploratory =seal-exec.sh= could build this narrower rsync
invocation itself without immediately changing Seal.  Doing so would turn
observed use into evidence about whether Seal eventually wants a queue-specific
transport operation.

*** A cooperative mailbox lock

Another possibility is an operator-created lock that tells the agent the
operator temporarily owns mailbox reconciliation.  While the lock is visible,
the agent may stage work elsewhere but knows that publishing into the locked
tree can be clobbered.

For an SSH-backed mailbox, creating a lock only in the operator's local copy is
insufficient: the lock must become visible on the peer before the final pull.
The useful ordering is approximately:

#+begin_example
make lock visible to agent
pull final ready state
prune claimed commands locally
push ready with deletion
remove peer-visible lock after successful push
#+end_example

Removing the lock before the destructive push reopens the race: the agent may
observe an unlocked mailbox and publish a command that the stale sender then
deletes.  Folding lock deletion into the same rsync can also leave a smaller
ordering question if the agent observes removal while receiver-side deletions
are still occurring.  Explicit release after successful reconciliation says
the intended thing more plainly.

This lock may remain cooperative rather than adversarially sound in v0.1.  A
mere presence check has check-then-publish races unless agent publication and
operator acquisition share a stronger primitive.  The exploratory question is
whether the actual single-agent workflow needs more than a visible convention,
not whether the first shell script can prove distributed mutual exclusion.

A stranded lock after operator interruption needs a manual recovery story or a
lease timestamp.  That friction may itself reveal whether locking belongs in
the eventual transport or was only useful prototype scaffolding.

*** A writable mailbox includes authority-shaped files

If the proposed command can write all of =mailbox/=, it can rewrite
=command.toml=, other ready commands, captured output, and =result.toml=.  That
weakens the otherwise-firm relationship between displayed proposal, launch,
and result.

A small alternative is to keep =seal-exec.sh= outside the sandbox, let the
parent script own queue transitions and result capture, and give the proposed
command write access only to =mailbox/world/= plus any deliberately assigned
per-command working area.  Standard output and standard error can cross the
boundary through the parent without giving the child write access to their
destination files.

This alternative is not yet a commitment.  It identifies the smallest place
where "allow writes inside mailbox" and "the exec operation must be firm" pull
against one another.

*** Explicit argv must stay argv (earlier variant)

The quick shell broker still needs to turn TOML strings into an argv vector
without =eval=, shell re-parsing, or concatenation.  Heavy semantic validation
can be omitted; lossless argument boundaries cannot.  Otherwise the displayed
proposal and executed command are different languages.

The initial =command.sh= spike avoided this parser boundary by executing exact
reviewed shell bytes.  The current argv experiment returns to the structured
proposal and implements the lossless boundary with strict TOML parsing and
NUL-delimited transfer into a held Bash array.

*** Output capture is part of the experiment's evidence

If output is displayed through =tee=, the broker must still preserve the
command's exit status and finish writing both streams before it records and
pushes the result.  This is mechanical bookkeeping rather than command-safety
policy, but getting it wrong would make the returned evidence unreliable.

*** Refusal and interruption remain visible questions

Claiming before the prompt raises a small lifecycle question: after the
operator declines, does the command remain claimed with a refusal result,
return to ready, or wait for manual cleanup?  Likewise, interruption after
launch but before =result.toml= cannot honestly become an automatic retry.
The prototype can use crude states, but it must not confuse them silently.

* Questions still alive

- What exactly is one proposal: argv, script text, a directory, or another
  finite object?
- How does an agent finish writing a proposal in a mutable intake directory?
- At what moment does Seal acquire stable proposal identity?
- What does operator-side attestation look and feel like?
- Is attestation separate from execution, or one deliberate interaction?
- Which failures are retryable publication failures, and which create an
  unknown execution outcome?
- What operator recovery surface republishes a result after post-execution
  transport failure without exposing an execution retry?
- Is filesystem modification time sufficient for strict-newest identity, or
  will the dialogue eventually need an explicit sequence relation?
- How much of a command directory returns to the agent?
- What minimum result must survive output-file clobbering?
- When does a world-reconciliation recipe run, and what does its success mean?
- Which runtime facts remain operator knowledge, and which eventually earn a
  first-class Seal representation?
- Does recurring friction eventually favor a restricted runner, or does the
  permissive operator-mediated path remain the primary product?
- Which protections are necessary for exploratory honesty, and which would be
  guesses about a production contract that does not yet exist?
- How small can the firm =exec= waist be while the surrounding shell broker
  remains easy to replace?

* Method correction

This session is wayfinding and fog-clearing, not code-contract litigation.
Earlier attempts to translate every distinction immediately into immutable
objects, generations, database rules, or CLI verbs overfit the discussion.

The record should preserve pressure and uncertainty until a smaller product
hypothesis becomes visible.  Code-facing precision will matter later.  It
should answer this exploration rather than terminate it.

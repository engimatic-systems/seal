#+title: Seal v0.1 experimental mailbox contract
#+date: 2026-07-16
#+options: toc:2 num:nil

* Status

This document teaches an agent how to use the experimental one-shot command
broker on the =seal-v0.1= branch.

This is a workflow convention, not a security proof or stable protocol.  The
operator may replace it as the experiment changes.  A copy placed in a mailbox
is a courtesy copy; the copy committed with Seal is the reference record.

The operator normally runs a watch loop.  It polls for proposals but stops for
human review before every execution.  Publishing a command does not authorize
it.

* Mailbox shape

#+begin_example
mailbox/
  contract.org
  ready/
    <command-id>/
      command.toml
  claimed/
    <command-id>/
      command.toml
      result.toml
      ...files written by the command...
  output/
    <command-id>.out
    <command-id>.err
  world/
    ...persistent working state...
#+end_example

The agent publishes under =ready/=.  The operator claims under =claimed/=.
Captured process output lands under =output/=.  Commands run with =world/= as
their current directory.

* Agent workflow

** Before proposing

Read this contract and inspect the current mailbox:

- =claimed/= and =output/= show earlier disposition and results;
- =world/= contains persistent working state created by earlier commands; and
- a =ready/<command-id>/= entry may remain visible even after claim because
  Seal v0 does not propagate ordinary deletions.

Presence of =claimed/<command-id>/= wins over a duplicate
=ready/<command-id>/=.  Never reuse a command ID.

Publish only one unclaimed proposal at a time.  Wait for its terminal result
before proposing the next command.  Multiple unclaimed proposals signal
protocol drift: strict newest wins and every older proposal is marked
=superseded= without execution.

** Prepare one command

Choose a unique ID containing only ASCII letters, digits, period, underscore,
and hyphen.  Its first character must be alphanumeric.  A UTC timestamp plus a
short description is useful:

#+begin_example
20260716T151500Z-clone-terraform
#+end_example

Create one regular, non-symlink =command.toml=.  Prepare the directory outside
=ready/= when practical, then rename it into =ready/= only after all proposed
files are complete.  The current transport is not a transactional queue; this
staging convention merely reduces partial proposals.

Do not modify a command after publishing it.  A changed request should receive
a new ID.

** Write =command.toml=

=command.toml= requires a nonempty array named =argv= and permits one optional
top-level string named =cwd=.  Every argv element must be a string, and
=argv[0]= must not be empty:

#+begin_src toml
cwd = "terraform"
argv = ["git", "status", "--short", "--branch"]
#+end_src

The broker preserves argument boundaries and executes this vector directly.
It does not apply shell splitting, expansion, interpolation, redirection, or
pipeline syntax.  Characters such as spaces, glob metacharacters, dollar
signs, and quotes remain part of their containing argument.

Bare executable names resolve through the inherited =PATH=.  If shell semantics
are genuinely the intended command, name the shell explicitly:

#+begin_src toml
argv = ["bash", "-lc", "printf '%s\\n' \"$VALUE\" > result.txt"]
#+end_src

Prefer one small, independently consequential operation that the operator can
review and that a later command can correct.  Use TOML comments to explain
intent or cheap preconditions.

=cwd= defaults to ="."=, meaning =mailbox/world/=.  A supplied cwd must be a
nonempty relative path without =..= components.  It must already name a
directory whose resolved physical location remains beneath =world/=.  Absolute
paths, missing directories, and symlinks escaping =world/= are invalid.  To
create a future cwd, first propose from the default cwd:

#+begin_src toml
argv = ["mkdir", "-p", "terraform"]
#+end_src

Do not add fields for environment, redirection, or sequencing; the current
broker rejects unknown top-level keys.

Do not assume that publication implies approval.  The operator may decline or
edit the TOML.

** Wait for disposition

The operator's =seal-exec.sh= watch loop pulls the mailbox repeatedly.  It
selects the most recently modified ready command that has no same-ID claimed
entry.  When modification times tie, the lexicographically greatest ID wins.

If several unclaimed proposals appear together, the newest is the only one
reviewed.  Every older proposal moves to =claimed/= with a =superseded= result
naming the winning command.  Do not treat the mailbox as a backlog.

The broker snapshots and parses =command.toml=.  The operator sees its numbered
exact bytes, a SHA-256 digest, requested and resolved cwd, and every parsed
argument rendered separately.  The operator then chooses:

- =yes=: execute the displayed argv;
- =edit=: edit it in =vi=, reparse, redisplay, and decide again; or
- anything else: refuse it.

Editing changes the executed proposal.  Inspect =edited= and the claimed
=command.toml= when interpreting the result.  Invalid TOML cannot reach =yes=;
the operator may edit it or reject it with an =invalid= result.

** Read the result

Seal returns:

- =output/<command-id>.out=: captured standard output;
- =output/<command-id>.err=: captured standard error; and
- =claimed/<command-id>/result.toml=: disposition and attempt metadata.

Normal completion resembles:

#+begin_src toml
status = "completed"
command_id = "20260716T151500Z-clone-terraform"
command_sha256 = "..."
edited = false
execution_mode = "direct"
started_at = "2026-07-16T15:16:00Z"
finished_at = "2026-07-16T15:16:03Z"
exit_code = 0
#+end_src

Known status values in the spike are:

- =refused=: operator did not authorize execution;
- =invalid=: =command.toml= was missing, non-regular, or failed argv validation;
- =superseded=: a newer proposal won when several were outstanding;
- =started=: execution began but the local result has not reached completion;
- =completed=: the process exited; inspect =exit_code= for success or failure.

After a known failure, inspect returned evidence and current world state, then
propose a new command under a new ID.  Fail forward rather than asking the
operator to replay an old attempt.  Even an intentional repetition is a fresh
proposal and receives fresh attestation.

An absent or incomplete remote result does not prove that execution never
began.  Transport happens after execution.  Ask the operator rather than
automatically resubmitting an effectful command whose outcome is uncertain.

Files written elsewhere in the mailbox are ad-hoc workspace or result
material.  Seal attributes only the captured streams and =result.toml=
mechanically.

* Execution world

Execution mode belongs to the operator invocation, not the proposal.  The
current spike defaults to =direct=; an operator may instead start the broker
with =--bwrap=.  =result.toml= records the selected mode.

In either mode, proposed argv runs with:

- current directory =mailbox/world/<cwd>/=, with ="."= as the default;
- the broker's inherited environment as captured when the watch process
  started, including =PATH=, credentials, and any active =mise= context;
- =TMPDIR= set to =mailbox/world/.tmp=;
- ordinary network access unchanged.

In default direct mode, the command has the operator process's ordinary host
permissions.  It can read or write any path available to that account,
including Seal's host-local broker state and credential state.  Initial cwd
containment does not constrain later filesystem access.

In optional =--bwrap= mode, the host filesystem is mounted read-only, the whole
mailbox is mounted writable, and the approved =command.toml= snapshot is mounted
read-only over its claimed path.

The writable =world/= is intended to carry state between commands: cloned
repositories, Terraform working directories, saved plans, and similar
material.  A later proposal may depend on state created by an earlier command.

The whole mailbox is technically writable so commands may leave ad-hoc files
beside their claimed request.  By convention, do not rewrite queue lifecycle,
other commands, captured outputs, or =contract.org= unless that mutation is the
explicit reviewed purpose.

Neither mode makes a command harmless.  A command may read host material, use
inherited credentials, access the network, and mutate external systems such as
Azure.  Direct mode additionally permits host filesystem mutation.  The
operator's review is the safety decision in this experiment.

Avoid printing credentials or copying secrets into mailbox files.  Everything
under the mailbox may return to the agent side.

Ambient environment values are not serialized into the proposal or result.
Changes made in another shell, or environment configuration created after the
watch process starts, do not update that running process.  Ask the operator to
restart watch from a reconciled environment when freshness matters.

* Example: establish repository state

The agent might first publish:

#+begin_src toml
argv = ["git", "clone", "--", "https://example.invalid/terraform.git", "terraform"]
#+end_src

After observing that result, a later proposal can inspect persistent state:

#+begin_src toml
cwd = "terraform"
argv = ["git", "status", "--short", "--branch"]
#+end_src

Another can use the same cwd for a =tofu plan= argv.  Repository state remains
an implicit part of the operator-understood world; Seal does not attest Git
semantics in this spike.

* Purge behavior

The operator may explicitly run =seal-exec.sh purge=.  After a literal =purge=
confirmation, it replaces both operator and agent mailboxes with a fresh shape
containing this contract and empty =ready/=, =claimed/=, =output/=, and
=world/= directories.

Purge intentionally destroys proposals, results, captured output, and world
state.  There is no agent/operator lock protocol yet.  Do not publish while a
purge is in progress.  After reset, reread the fresh contract and begin with a
new unique command ID.

* Non-claims

This spike does not provide:

- agent-side polling, scheduling, or notification;
- semantic command-safety validation or a claim that reviewed argv is safe;
- isolation from network or external credentialed effects;
- transactional shared-directory queue semantics;
- reliable deletion propagation during ordinary claim;
- immutable or exhaustively represented world state;
- automatic retry after an uncertain execution; or
- a stable protocol promised to future Seal versions.

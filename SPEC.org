#+title: Seal v0 Specification

* Status

This specification defines the first usable Seal. It governs v0 implementation
when earlier design notes, tickets, or abandoned branches imply more behavior.

The =P, W, A, E, R= trace remains useful for describing the surrounding manual
workflow. Seal represents or attests none of those objects.

* Purpose

Seal moves one opaque mailbox directory between a peer location and an
operator-controlled directory using rsync. The peer may be another local
directory or a path reached through SSH.

Seal replaces manual file copying. It does not replace human review, decide
what mailbox entries mean, or execute anything found in the mailbox.

#+begin_example
agent writes peer mailbox
operator runs seal pull
operator inspects arbitrary mailbox material and local circumstances
operator may manually run or modify material outside Seal
operator may place arbitrary material in the local mailbox
operator runs seal push
agent reads peer mailbox
#+end_example

* Minimal implementation rule

Minimality is part of the v0 contract, but it is not code golf. Seal v0 should
be the smallest clear implementation that supports the demonstrated operator
workflow and preserves the historical safety boundaries below.

A field, abstraction, validation rule, dependency, or test belongs only when
required by current behavior, a previously observed exploit class, or evidence
from the live smoke. Prefer clear duplication over premature reuse. Report one
clear configuration error rather than building an error aggregation system.
Test the working path and consequential invariants; do not enumerate library
behavior or hypothetical failures.

Expansion follows observed friction. Anticipated convenience or hardening is
deferred until the working executable demonstrates the need.

* Contract boundary

** Authority direction

- Every transfer is initiated by the operator.
- Seal exposes no listener, server, callback, approval endpoint, execution
  endpoint, watcher, or background synchronization.
- A peer may mutate its mailbox at any time.
- Peer mutation reaches the local mailbox through Seal only when the operator
  invokes =seal pull=.
- Local mutation reaches the peer mailbox through Seal only when the operator
  invokes =seal push=.

Host initiation limits who can start a transfer. It does not make the peer or
transferred tree trustworthy. A local peer may remain independently writable
through ordinary filesystem topology.

** One mailbox

One configuration names one local mailbox and one peer mailbox. =pull= and
=push= reverse direction between those roots. Seal assigns no inbox, outbox,
proposal, result, request, or response roles to entries inside them.

** Opaque contents

Seal does not parse, lint, normalize, classify, hash, summarize, format, or
execute mailbox contents. Filenames, directory layout, file contents, and
executable bits carry no meaning to Seal.

Ordinary files, directories, and symbolic links are v0 material. Seal must not
ask rsync to dereference source symbolic links. A transferred symbolic link
remains a link; Seal makes no claim about its target or about later use.

* Configuration

** Discovery

Seal reads =./seal.toml= by default. =--config PATH= selects another file. Seal
does not search parents, user directories, system directories, or environment
variables.

Relative local paths resolve from the selected configuration's directory. An
SSH peer path remains a peer-side path.

** Syntax

Configuration is a deliberately small line-oriented syntax, not general TOML.
Each line is trimmed only of leading and trailing spaces and tabs. Blank lines
are accepted; comments are not accepted outside strings.

A table line is =[=, one key, then =]= with no internal whitespace. An
assignment is one key, optional horizontal whitespace, ===, optional horizontal
whitespace, and one string. A key starts with an ASCII letter and continues
with ASCII letters, digits, or underscore. A string is double-quoted printable
ASCII excluding double quote and backslash; it has no escapes. The complete
trimmed line must be consumed. Lists, Unicode, control bytes, trailing syntax,
and other value forms are rejected.

** Fields

#+begin_src toml
local_mailbox = "mailbox"

[peer]
path = "/home/agent/mailbox"
ssh = "experiment.agent"

[tools]
rsync = "/run/current-system/sw/bin/rsync"
ssh = "/run/current-system/sw/bin/ssh"

[debug]
rsync_debug_flags = "-v"
ssh_debug_flags = "-v"
#+end_src

Omitting =peer.ssh= makes =peer.path= local. A local peer omits =tools.ssh= and
=debug.ssh_debug_flags=. An SSH peer requires both =peer.ssh= and =tools.ssh=.

=peer.ssh= is one opaque SSH destination argument such as =user@host= or an
alias from the operator's SSH configuration. Seal does not parse SSH config,
hostnames, usernames, or destination syntax.

=tools.rsync= and optional =tools.ssh= are absolute local executable paths
resolved and recorded by =seal init=. Seal invokes those paths instead of
consulting =PATH= on every transfer. Pinning a path does not attest its bytes.

The peer rsync executable is selected by the peer's ordinary remote environment.
V0 does not configure =--rsync-path= or perform remote executable discovery.
The live smoke determines whether that becomes concrete friction.

The optional =debug= table controls diagnostic verbosity only when global
=--debug= is present. Each applicable scalar is =""=, ="-v"=, ="-vv"=, or
="-vvv"=. Missing fields default to ="-v"=. No other SSH or rsync debug syntax
and no arbitrary flag passthrough is accepted in v0.

The fixed transfer flags are not configuration. The specification and obvious
constants in =SEAL.org= own them.

* Command surface

** Global options

=--config PATH= selects configuration. =--debug= explains selection, resolved
values, and subprocess plans on standard error.

** =seal init=

#+begin_src sh
seal init ../other-mailbox
seal init /home/agent/mailbox --ssh experiment.agent
#+end_src

=init= creates =seal.toml= and one local =mailbox/= directory in the selected
configuration directory, which defaults to the current directory. It resolves
and records local rsync and, for an SSH peer, local SSH.

=init= does not contact the peer or create a peer directory. It refuses an
existing configuration or conflicting mailbox path. It preflights those known
conflicts; v0 does not implement a general filesystem transaction framework.

** =seal cfg=

=cfg= parses and prints the selected configuration, selection reason, resolved
local paths, peer coordinates, pinned local tools, debug flags, binary version,
and fixed transfer profile. It does not inspect mailbox contents, contact the
peer, invoke external tools, or modify state.

** =seal pull=

=pull= invokes pinned local rsync with the peer mailbox as source and the local
mailbox as destination. =pull --dry-run= asks the same plan to report intended
changes without applying them.

** =seal push=

=push= invokes the same transfer machinery with the local mailbox as source and
the peer mailbox as destination. =push --dry-run= asks the same plan to report
intended changes without applying them.

Neither transfer command executes mailbox content, invokes the other direction,
retries automatically, or interprets child output as approval.

* Transfer semantics

Each transfer is one explicit directional update. V0 has no reconciliation,
conflict detection, merge, retry, whole-tree atomicity, history, manifest, or
deletion propagation. Destination-only entries remain.

The fixed ordinary profile is:

#+begin_example
--recursive
--links
--perms
--times
--checksum
#+end_example

SSH peers additionally use =--secluded-args= and the pinned SSH executable as
rsync's remote shell. Both mailbox operands use trailing slashes, and =--=
separates fixed options from operands.

The profile intentionally omits deletion, source-link dereferencing, owner and
group preservation, devices, special files, ACLs, extended attributes,
hard-link identity, compression, partial-file retention, and automatic
destination creation.

=SEAL.org= defines ordinary and SSH-only transfer flags as small, obvious
constants. They are not configurable.

Seal represents a process plan as executable plus structured argv and invokes
rsync directly without a local shell. Rsync remains responsible for its SSH
operation. Useful child output remains recognizable. Child failure causes Seal
to return nonzero; partial destination changes may remain.

* Debug behavior

As applicable, =--debug= reports:

- process working directory;
- selected and resolved configuration path;
- effective configuration and resolved local paths;
- exact subprocess executable and argv as structured values; and
- child exit status.

Debug adds only the configured =-v=, =-vv=, or =-vvv= value. It must not change
endpoints, deletion behavior, symlink handling, or other transfer semantics.

Seal messages use plain labels:

#+begin_example
[info] :: something
[warn] :: something
[error] :: something
[debug] :: something
#+end_example

A small local function is sufficient. V0 has no logging dependency or logging
framework. Child output is not rewritten into Seal messages.

* Failure posture

- Invalid configuration fails before transfer with one useful error.
- Missing local prerequisites fail when Seal encounters them.
- SSH, rsync, and peer failures remain visible failures.
- Failure may leave a partially changed destination.
- Recovery remains an operator decision using Seal or ordinary tools.

* Non-claims

Seal v0 does not provide automated execution; proposal or result schemas;
approval or attestation; shape matching; immutable snapshots; history or replay
protection; symlink-target safety; sandbox escape prevention; credential
management; peer provisioning; a daemon or UI; multiple mailboxes; or another
transport.

=seal doctor= is also deferred. Its retained ticket defines a possible later
diagnostic command; it is not required for v0 completion.

These omissions are boundaries, not hidden behavior.

* Implementation readiness

V0 is ready for a serial implementation train. When live smoke reveals missing
behavior, record the friction before expanding the contract. Convenience alone
does not authorize scope growth.

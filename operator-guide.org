#+title: Seal v0.1 spike operator guide
#+date: 2026-07-16
#+options: toc:2 num:nil

* Status

This guide tells an operator how to exercise the experimental one-shot command
broker on the =seal-v0.1= branch.

The broker is a watched manual spike, not a daemon or hardened security
boundary.  It polls automatically, processes one proposal at a time, and
stops for operator review before every execution.

The agent-facing workflow is recorded separately in [[file:contract.org][contract.org]].  Copy that
file into the mailbox so an agent can discover the current convention.

* Requirements

Run the spike on Linux with:

- a built =seal= binary;
- Bash and ordinary GNU userland tools;
- =bwrap=;
- =rsync=;
- =vi=; and
- Python 3 with =tomllib=.

An SSH-backed peer also requires =ssh=.  =seal init= records absolute paths to
the =rsync= and =ssh= executables it discovers, so initialize from the intended
operator environment.

Keep =seal-exec.sh= outside the mailbox.  Run it from the root of an operator
workspace containing =seal.toml= and =mailbox/=.

* Build the spike

From the Seal source checkout:

#+begin_src bash
git switch seal-v0.1
cargo build

SEAL_SOURCE="$(pwd)"
SEAL="$SEAL_SOURCE/target/debug/seal"
BROKER="$SEAL_SOURCE/seal-exec.sh"
CONTRACT="$SEAL_SOURCE/contract.org"
#+end_src

Keep these shell variables available for the commands below, or replace them
with absolute paths.  Reconcile the repository's expected tool environment
before building when Cargo is not already available.

* Create an operator workspace

Choose an empty directory outside both the source checkout and agent mailbox:

#+begin_src bash
mkdir -p /path/to/operator-workspace
cd /path/to/operator-workspace
#+end_src

Ensure the peer mailbox directory already exists and is reachable.  For a
local peer:

#+begin_src bash
"$SEAL" init /path/to/agent-mailbox
#+end_src

For a peer reached through an existing SSH destination:

#+begin_src bash
"$SEAL" init /path/on/agent-host/mailbox --ssh agent-alias
#+end_src

Initialization creates exactly:

#+begin_example
operator-workspace/
  seal.toml
  mailbox/
#+end_example

It refuses an existing configuration or local mailbox rather than adopting
one.  Inspect the effective coordinates and pinned tools with:

#+begin_src bash
"$SEAL" cfg
#+end_src

* Publish the agent contract

First hydrate the local mailbox from the peer.  Then add the contract to the
local copy and push it:

#+begin_src bash
"$SEAL" pull
cp "$CONTRACT" mailbox/contract.org
"$SEAL" push
#+end_src

The committed =contract.org= is the reference record.  Its mailbox copy is
agent-readable guidance and may be replaced as this experiment changes.

* Watch for proposals

The agent publishes a proposal with this minimum shape:

#+begin_example
mailbox/
  ready/
    <command-id>/
      command.toml
#+end_example

=command.toml= contains exactly one nonempty string array:

#+begin_src toml
argv = ["git", "-C", "terraform", "status", "--short", "--branch"]
#+end_src

The broker rejects other top-level fields.  It executes argv directly without
shell parsing.  A proposal may request a shell explicitly when needed, for
example =argv = ["bash", "-lc", "..."]=.

From the operator workspace root, run:

#+begin_src bash
cd /path/to/operator-workspace
SEAL_BIN="$SEAL" "$BROKER" watch
#+end_src

=watch= is the default, so omitting it has the same effect:

#+begin_src bash
SEAL_BIN="$SEAL" "$BROKER"
#+end_src

The broker performs this cycle:

#+begin_example
seal pull
  -> no proposal: wait two seconds, then pull again
  -> choose strict newest unclaimed ready command
       multiple: warn and mark every older proposal superseded
  -> move ready/<id> to claimed/<id>
  -> snapshot and parse command.toml
       invalid: offer edit or record invalid result
  -> show ID, SHA-256 digest, numbered TOML, and indexed argv
  -> ask operator
       yes   -> execute
       edit  -> open vi, then reparse, show, and ask again
       other -> refuse
  -> write disposition and captured output
  -> seal push
  -> wait two seconds, then pull again
#+end_example

Typing =edit= changes the proposal under review.  After editing, review the
redisplayed bytes, digest, and parsed arguments; the result records =edited= as
=true=.

The agent is expected to publish one command, poll for its terminal result,
then publish the next.  Multiple unclaimed proposals signal protocol drift.
The broker still behaves deterministically: newest wins and older proposals
receive =superseded= results without execution.

Press =Ctrl-C= to stop watching.  For one pull/review iteration instead, run:

#+begin_src bash
SEAL_BIN="$SEAL" "$BROKER" run
#+end_src

If nothing is ready, =run= reports that fact and exits without pushing.  After
a completed command, =run= returns that command's exit code; =watch= records
the exit code and continues so the agent can fail forward.

* Inspect results

After disposition:

#+begin_example
mailbox/
  claimed/
    <command-id>/
      command.toml
      result.toml
      ...ad-hoc command files...
  output/
    <command-id>.out
    <command-id>.err
  world/
    ...persistent working state...
#+end_example

=result.toml= reports =refused=, =invalid=, =superseded=, =started=, or
=completed=.  For a completed attempt, inspect =exit_code= rather than treating
completion as success.

Standard output and standard error are displayed during execution and retained
in =output/=.  After a successful result push, =run= returns the proposed
command's exit code; =watch= records it and resumes polling.

Ordinary Seal synchronization does not propagate deletion.  The peer may
therefore retain =ready/<id>/= after the operator has claimed it.  Presence of
=claimed/<id>/= wins, and the broker will not execute that duplicate.

* Execution boundary

Approved argv runs directly under =bwrap= with:

- =mailbox/world/= as current directory;
- the whole mailbox writable;
- the exact reviewed =command.toml= snapshot mounted read-only at its claimed
  path;
- the rest of the host filesystem mounted read-only;
- =TMPDIR= set to =mailbox/world/.tmp=;
- the broker's inherited environment, including =PATH= and credentials; and
- network access unchanged.

There is no implicit shell splitting, expansion, interpolation, pipeline, or
redirection.  Bare =argv[0]= names resolve through inherited =PATH=.  Explicit
=argv = ["bash", ...]= restores shell semantics as part of the reviewed
proposal.

The inherited environment is the environment present when watch starts.  It is
not serialized into proposal or result evidence, and changes in another shell
do not update the running broker.  Stop and restart watch from a reconciled
environment when ambient variables need refresh.

This prevents ordinary host-filesystem writes outside the mailbox.  It does
not prevent reading host files visible in the namespace, using inherited
credentials, reaching the network, or mutating external systems.  Inspect for
those effects before typing =yes=.

Everything written under the mailbox may be transported back to the agent.
Do not expose secrets through proposals, output, or ad-hoc result files.

* Purge and reinitialize the mailbox

To destroy both mailbox copies and reinstall a fresh shape:

#+begin_src bash
cd /path/to/operator-workspace
SEAL_BIN="$SEAL" "$BROKER" purge
#+end_src

The broker displays the scope and requires the literal response =purge=.  It
stages a mailbox containing the current =contract.org= and empty =ready/=,
=claimed/=, =output/=, and =world/= directories.  It deleting-syncs that shape
to the peer, then replaces the local mailbox only after peer synchronization
succeeds.

Purge destroys proposals, dispositions, captured output, ad-hoc files, and
persistent world state on both sides.  Host-only evidence under
=.seal-exec/attempts/= is retained.

Purge has no mailbox lock.  Agent writes concurrent with the deleting sync may
be destroyed or leave a mixed result.  Stop the watch loop and coordinate with
the agent before purging.

* Interrupted attempts

Execution records local attempt state under:

#+begin_example
operator-workspace/.seal-exec/attempts/<command-id>/
#+end_example

If execution or transport is interrupted, do not infer non-execution from an
absent remote result.  Inspect local attempt state, =claimed/<id>/result.toml=,
captured output, persistent world state, and any external system affected by
the command.  Do not resubmit an effectful operation until its outcome is
known.

#+title: Seal v0 Implementation Plan

* Planning premise

Seal replaces Bridge and Airlock by automating transport only. Earlier
implementations accumulated command shapes, reusable authority, automated
execution, and sandbox-reachable control surfaces. V0 must not reconstruct
those surfaces.

The first implementation attempt also demonstrated a different failure: an
exhaustive specification, evidence matrix, and reviewer ratchet can make a
small transport wrapper large before an operator touches it. This revision
makes minimality an implementation constraint.

Build the smallest clear artifact that supports the current car. Add a field,
type, helper, dependency, validation rule, or test only for present behavior, a
historical safety boundary, or observed smoke-test friction. Do not optimize
for hypothetical completeness.

* Pipeline

#+begin_example
operator invokes verb
  -> select and parse local config
  -> construct one directional transfer plan
  -> explain plan when debugging or dry-running
  -> invoke pinned local rsync, which may invoke pinned local SSH
  -> relay output and status
#+end_example

Mailbox bytes remain opaque. =init= creates local state. =cfg= stops after
configuration inspection.

* Source and evidence

=SPEC.org= is the behavioral contract. =PLAN.org= records sequence and review
questions. =SEAL.org= is the literate implementation source.

Each implementation car must retangle, leave a clean second tangle, format,
test its current consequential behavior, and build. Evidence should be compact:
commands, exit status, and one representative interaction. Test count is not a
measure of completeness.

Pseudocode belongs immediately before consequential source blocks. Split
blocks only at stable file or top-level Rust boundaries. Generated dependency
locks remain generated artifacts rather than literate source.

* PR train

** PR 1: Executable Seed

Goal: produce one inspectable executable and reproducible literate build loop.

Deliverables:

- =SEAL.org= and a tangled Rust package;
- =seal --help= and =seal --version=;
- global =--debug= with current-directory and version facts;
- small local functions for Seal's plain diagnostic labels; and
- only enough CLI testing to pin visible seed behavior.

Out of scope: config, mailbox creation, SSH, rsync, later-verb stubs, and a
logging abstraction.

Evidence: clean second tangle, build, tests, and one help/debug transcript.

Review question: is this the smallest readable executable seed that establishes
the literate workflow?

** PR 2: Configuration And =cfg=

Goal: parse and display the exact coordinates later commands will use.

Deliverables:

- explicit =--config PATH= or default =./seal.toml= selection;
- local mailbox, peer path, optional SSH destination, and pinned local tools;
- local path resolution relative to the config directory;
- optional =ssh_debug_flags= and =rsync_debug_flags= accepting only an empty
  value or one of =-v=, =-vv=, and =-vvv=, defaulting to =-v=;
- read-only =seal cfg=; and
- first clear error for invalid configuration.

Out of scope: aggregate error reporting, remote tool pinning or discovery,
filesystem creation, peer contact, and subprocess execution.

Evidence: one valid local fixture, one valid SSH fixture, one invalid fixture,
and representative =cfg= output.

Review question: can the operator inspect effective behavior without Seal
inventing a configuration framework?

** PR 3: Local =init=

Goal: create one current-directory Seal workspace without contacting the peer.

Deliverables:

- =seal init PEER_PATH= and optional =--ssh SSH_DESTINATION=;
- one =seal.toml= and one local =mailbox/=;
- pinned local rsync and conditional SSH executable paths; and
- refusal to overwrite known config or mailbox conflicts.

Out of scope: peer contact, peer provisioning, remote executable selection,
general filesystem transactions, transfer, and global state.

Evidence: local init, SSH init, conflict refusal, and config round-trip.

Review question: does =init= create only the local state needed to try Seal?

** PR 4: =pull=

Goal: perform one explicit peer-to-local opaque mailbox transfer.

Deliverables:

- one process plan represented as executable plus structured argv;
- obvious constants for the fixed rsync profile;
- =seal pull= and =seal pull --dry-run=;
- direct child invocation without a local shell;
- local and SSH operands with exact debug rendering; and
- child failure propagation.

Out of scope: push, retry, rollback, deletion, source-link dereference,
content inspection, remote executable pinning, and configurable transfer flags.

Evidence: exact local and SSH argv, child failure status, one local rsync
transfer, and one symlink fixture proving the link is not dereferenced.

Review question: does =pull= perform exactly one visible transfer with no
mailbox interpretation or hidden authority?

** PR 5: =push=

Goal: reverse the same transfer plan with minimal additional machinery.

Deliverables:

- =seal push= and =seal push --dry-run=;
- local mailbox as source and peer mailbox as destination; and
- reuse of the reviewed transfer planner and fixed profile.

Out of scope: publication semantics, result classification, delivery records,
conflict resolution, retry, and push-specific configuration.

Evidence: exact reversed operands and one working local push.

Review question: is =push= a small direction reversal rather than a second
transport implementation?

** PR 6: Live SSH Smoke

Goal: use the integrated artifact and let concrete friction determine future
work.

Deliverables:

- a disposable SSH-backed workspace using the experiment VM;
- =init= and =cfg= transcript;
- peer mailbox containing nested directories, regular files, and a symlink;
- pull, ordinary local modification, and push;
- dry-run in both directions;
- retained destination-only entries;
- one unreachable-host failure; and
- a compact =VALIDATION.org= with cleanup and observed friction.

Leave =agent-dayjob-01= powered off. The smoke owns evidence, not convenience
features. Contract-blocking defects may be repaired; other findings become
later tickets.

Out of scope: =doctor=, running pulled material, VM lifecycle repair, new
commands, new transfer options, and speculative diagnostics.

Evidence: commands, statuses, before/after trees, preserved symlink identity,
failure status, cleanup, and a short friction list.

Review question: is this artifact sufficient for the operator to perform the
manual mailbox round trip, and where did actual use hurt?

* Sequencing and review

The train is serial:

#+begin_example
seed -> config/cfg -> init -> pull -> push -> live SSH smoke
#+end_example

Dispatch one cold worker for one ready car. Give it the accepted specification,
assigned ticket, current base, and minimality rule rather than full conversation
history. Do not prebuild the train tail.

The operator reviews each tactile artifact before the next car advances. No
independent reviewer agent is required during construction. The coordinator
checks topology, scope, build, representative behavior, and unexplained code
growth; it does not demand broader tests as a default review response.

After live smoke, a separate reduction review may identify deletable code,
tests, dependencies, and fields. That review must not add behavior or broaden
tests unless deletion exposes a demonstrated contract failure.

* V0 completion

V0 is complete when an operator can initialize and inspect one workspace,
preview and perform explicit pull and push operations, inspect the exact plans,
observe child failure, and complete a live SSH mailbox round trip.

Completion does not require =doctor=, remote executable pinning, exhaustive
validation, automated execution, approval, attestation, mailbox schemas,
history, deletion, multiple mailboxes, or another transport.

* Deferred work

=seal doctor= retains its own ticket as a possible post-v0 diagnostic feature.
Its current definition is not evidence that v0 needs it.

Any other expansion begins with observed friction or a new specification
question after the working executable exists.
